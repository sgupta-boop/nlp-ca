LLM-Assisted Product Entity Resolution

Attribute Extraction, Semantic Embeddings and Hybrid Matching for Product Name Standardization

October 2026Hardware: Windows 11 · 7.4 GB RAM · GTX 1650 Ti (4 GB)LLM: qwen3:8b (local, Ollama)
Abstract

Online catalogues describe the same product with different column names and differently written product names. We present a pipeline that maps any product table to one schema, selects the text worth comparing, normalizes and parses product names, extracts attributes, and groups listings of the same product. It combines rules, string similarity and cosine similarity of embeddings, and calls a local large language model only where cheaper methods are uncertain.

On labelled benchmarks it maps column headers with 96.6 % accuracy, normalizes units with 98.8 % exact match, reaches pair-matching F1 0.753 on Abt-Buy (0.529 without attribute rules), and the LLM decides 84.6 % of the most uncertain pairs correctly against 66.2 % for the threshold.

1Introduction

When two shops list the same item, the records rarely agree. Columns are named product, title or Item Name; quantities are written 1kg, 1000 gm or 1 kilo; model numbers appear as PS-LX350H or PSLX350H. Deciding which records refer to the same real product is called entity resolution.

The original project idea standardized columns and grouped names with rules, string similarity and cosine similarity. Following the professor's feedback, the project was rebuilt around NLP (tokenization, normalization, lemmatization, named-entity recognition, text representations) and uses large language models only where they measurably add value. Every claim in this report is backed by a number measured on a labelled test set.

4Column mapping and selection

Method

Every source column is mapped to one of ten fields (product_name, brand, category, sub_category, price, mrp, quantity, description, rating, id) or to other. Four mappers were compared: keyword rules on the header words; Sentence-BERT cosine similarity between the column (header plus five sample values) and a description of each field; the LLM alone; and the final cascade.

flowchart TD
  H[Column header + 5 sample values] --> T[Split header into words
snake_case and camelCase]
  T --> K{Keyword rule fires?
price, brand, name, id ...}
  K -- yes --> R[Field from rule]
  K -- no --> L[Ask LLM: which field?
answer = one of 11 labels]
  R --> P{Two columns both 'price'?}
  L --> P
  P -- yes --> M[Higher median value = mrp
MRP is never below price]
  P -- no --> O[Final field]
  M --> O

Keyword rules are strong because product-table headers are short and conventional. Embeddings with sample values do worst: the sample values dominate the sentence, so a description column whose samples read "5 x 10/100Base-TX LAN" is mistaken for a quantity. The cascade matches the best accuracy while calling the LLM for only 22 % of headers. The cascade was designed after seeing errors on the same 59 headers, so 0.966 is optimistic; the rules (0.898) and embeddings (0.644) were not tuned.

6Attribute extraction (NER)

Brand, product type, colour, quantity and pack count were extracted from 354 WDC-PAVE product titles by four methods: a spaCy EntityRuler with a brand gazetteer (8,000+ brands) and colour list; GLiNER zero-shot NER; the LLM with three examples and a Pydantic schema; and a small spaCy NER model trained on 2,000 names labelled by GLiNER (distillation).

Product names depend on brand names and model codes, which TF-IDF matches exactly and weights by rarity. Sentence embeddings are better at meaning (a washer is not a dryer; "carrying case" ≈ "carry case") but blur codes that differ by one character (GSD4000 vs GSD2400). Because the two families fail on different pairs, the matcher combines them. Phase 2 normalization raised mean Recall@1 across all representations from 0.672 to 0.711.

10Fine-tuning and the demo application

All-MiniLM-L6-v2 was fine-tuned with MultipleNegativesRankingLoss (in-batch negatives) on 8,471 WDC positive pairs and 6,000 synthetic pairs (typos, abbreviations, reordered words, with size-changed hard negatives), batch 64, one epoch, in 241 s on the GPU. The fine-tuned model is used by the application. Its comparison against the base and multilingual models (LaBSE, multilingual-E5) and the Hinglish robustness test were implemented but not run before the deadline.

13Limitations

  • LLM cost on a laptop. About 10–15 s per call (3.7 tokens/s, model 39 % on the GPU) forced small LLM budgets: 65 grey-zone pairs, 55 categorizations, 15 Hinglish items.
  • Gold-label provenance. The 59 headers, 500 BigBasket pairs and 15 Hinglish items were labelled during the project and must be checked by hand. The BigBasket labels used MRP as evidence, which flatters the MRP rule.
  • Tuning on small sets. The column-mapping cascade and three unit fixes were designed after looking at errors on the evaluation data; untuned figures are reported alongside.
  • Hinglish. The English model does not know that chawal means rice, and qwen3:8b rarely translated words into Hindi when asked to write test data.
  • Not run before the deadline. The fine-tuned vs base vs multilingual comparison, the six-configuration ablation table, and BERTopic category discovery are implemented (src/finetune.py, evaluate.py, topics.py) but have no results yet.

14Conclusion

We built a complete pipeline from messy product tables to clean product groups. Cheap, transparent methods do most of the work: keyword rules map 90 % of headers, a quantity grammar normalizes 98.8 % of units, and attribute rules raise matching F1 from 0.53 to 0.75. Lexical TF-IDF outperforms sentence embeddings for retrieving products, but the two fail on different pairs, which motivates the hybrid score.

The LLM is most useful where reasoning about product identifiers is needed and cheaper signals are uncertain: on the hardest pairs it is right 85 % of the time against 66 % for a threshold. It is not useful everywhere: it did not beat simple embeddings for categorization, and it is four orders of magnitude slower than the fastest extractor. Using it selectively is therefore a measured design choice, not an assumption.
